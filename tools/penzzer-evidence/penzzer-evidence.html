1.  Summary

Penzzer evaluates industrial control devices under malformed traffic, invalid state transitions, unauthorized protocol behavior, and resource stress, and produces reproducible evidence mapped to the IEC 62443 foundational requirement areas and to IPA's Cyber/Physical Security Framework (CPSF).

This document provides the technical and compliance evidence buyers need for OT security review, supplier qualification, and product security assessment. It is a standalone reference; it does not require a separate sales briefing.

1.1  Certification-readiness position

Penzzer does not claim IEC 62443 certification for the Penzzer product itself. Instead, Penzzer provides IEC 62443-aligned industrial fuzzing evidence that can support OT security review, supplier qualification, product security assessment, and certification-readiness activities.

Formal IEC 62443 product, component, system, or secure-development-lifecycle certification is issued by accredited certification bodies under recognized schemes such as ISASecure CSA, SSA, and SDLA. Penzzer evidence is structured as supporting technical material for internal assessors, customer audit teams, and external IEC 62443 / ISASecure assessment partners.

For Tier-1 engagements, an independent technical review may be included as part of the evidence package. The scope and reviewing laboratory are defined in the engagement test plan (see §13).

4.  Evaluation Scope

4.1  Assets under test

Penzzer evaluates: PLCs, RTUs, I/O modules, industrial gateways, protocol converters, engineering workstations, HMIs, embedded industrial devices, industrial network appliances, and simulated or emulated industrial protocol targets.

Each asset record includes manufacturer, model, firmware version, hardware version, configuration, network role, enabled protocols, safety limits, reset and recovery procedure, and known test constraints.

4.2  Test environment

Testing is performed in a controlled OT test environment. Live production control systems are tested only with explicit written authorization and operational safety controls in place.

The test environment is documented in every engagement: network topology, zone and conduit assumptions, test host configuration, monitoring points, packet capture location, device logging method, power-cycle and reset access, safety boundary, operational constraints, and stop conditions.

5.  Test Categories Executed

The standard evaluation model includes the following twelve protocol robustness categories. Each engagement documents which categories are applicable, executed, modified, or excluded based on protocol behavior, asset capability, safety constraints, and buyer-approved scope.

6.  Methodology

Phase 1 — Scope Definition

Protocols, asset under test, firmware version, safety boundaries, test categories, expected normal behavior, stop conditions, evidence requirements, severity model, and pass/fail criteria are agreed in writing before testing begins.

Phase 2 — Baseline Characterization

Expected protocol traffic, device response behavior, normal polling cycle, normal CPU and memory state, expected logs, expected alarms, expected control behavior, and recovery procedure are recorded.

Phase 3 — Campaign Preparation

Seed corpus, protocol grammar or state model, mutation strategy, target service inventory, authentication or session material, rate limits, safety limits, and monitoring and logging tooling are prepared.

Phase 4 — Campaign Execution

Campaigns are separated by protocol, target asset, and test category so findings are attributable.

Phase 5 — Monitoring

Network traffic, device responses, protocol errors, service availability, control behavior, process simulation state, device logs, CPU and memory usage, watchdog behavior, and restart and recovery behavior are observed.

Phase 6 — Triage

Observations are classified as Confirmed Finding, Safety-Critical Finding, Availability Finding, Protocol Robustness Finding, Logging or Detection Gap, Expected Behavior, False Positive, or Out of Scope.

Phase 7 — Replay and Reproducibility

Each confirmed finding includes protocol, target asset, firmware version, test category, payload or message sequence, preconditions, timing details, expected and observed behavior, evidence artifacts, recovery steps, reproducibility status, and IEC 62443 FR mapping.

Phase 8 — Reporting

The final report contains executive summary, scope, environment, safety controls, methodology, IEC 62443 and IPA CPSF mapping tables, protocol and category coverage summaries, confirmed findings, severity model, reproducibility evidence, recovery results, logging observations, limitations, recommendations, and an artifact index.

10.  Acceptance Criteria

A completed evaluation meets the following criteria:

  1. Asset under test is identified by manufacturer, model, and firmware version.
  2. Tested protocol scope is explicitly documented.
  3. Test environment and safety boundary are documented.
  4. Baseline normal behavior is captured.
  5. The applicability and execution status of each protocol robustness category is documented; omissions are explained.
  6. Execution logs and packet captures are retained.
  7. Confirmed findings are separated from anomalies and false positives.
  8. Recovery behavior is recorded for every availability-impacting finding.
  9. Findings are mapped to IEC 62443 FRs and IPA CPSF function categories.
  10. The report includes limitations and out-of-scope items.

12.  Scope of Claim

This document is a technical evidence brief, not a certification artifact. It does not represent IEC, ISA, or ISASecure certification, nor any accredited certification-body assessment. Penzzer evidence may be submitted as supporting technical material to such schemes; the certification decision is made by the accredited body.

13.  Independent Technical Review

For Tier-1 engagements, Penzzer may include an independent technical review as part of the evidence package. Independent review is also available for other engagements by mutual agreement.

The review may be performed by a mutually agreed external OT security laboratory, certification-preparation partner, or qualified industrial security assessor. The purpose of the review is to provide third-party assurance over the test plan, executed scope, evidence quality, finding reproducibility, and standards-alignment mapping.

The independent review may deliver: reviewed test plan, environment description, asset and protocol scope, executed category summary, confirmed findings summary, IEC 62443 alignment summary, limitations, and a signed technical review letter.

Important Unless expressly issued by an accredited certification body under a recognized certification scheme, the independent review letter does not constitute IEC 62443 certification, ISA approval, or ISASecure certification.
